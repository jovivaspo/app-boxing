### Approaches: drift-free wall-clock countdown

1. **Naive `setInterval` decrement** — explicitly rejected by the issue itself; drifts because browsers throttle/suspend intervals in backgrounded tabs, and decrementing a counter each tick accumulates error instead of recomputing from a fixed origin.
2. **`Date.now()` delta against a fixed phase-start timestamp, recomputed on every tick** — remaining time is always `duration - (Date.now() - phaseStartTime)`, never an accumulated decrement. Immune to drift/throttling because a missed or delayed tick just means the next recompute jumps to the correct value instead of compounding error. Needs a "wake me up to re-render" mechanism (interval or rAF) plus a `visibilitychange` listener that forces an immediate recompute the moment the tab becomes visible again (since the wake-up mechanism may not fire at all while hidden). Effort: Low-Medium. This is the actual anti-drift fix, independent of which trigger below is chosen.
3. **`requestAnimationFrame` as the render trigger** — smoother visual updates for the ring animation, but rAF is throttled or fully suspended in background tabs (browser-dependent) — it cannot be relied on alone to "wake up" the countdown; must be paired with approach 2's timestamp-delta math and a `visibilitychange`-forced recompute. Effort: Medium.
4. **Web Worker running `setInterval`** — workers are typically not throttled the same way as main-thread intervals when the tab is backgrounded. Pros: most robust against browser throttling. Cons: overkill complexity (cross-thread messaging) for a single boxing timer, no existing precedent in this codebase, adds a new architectural surface. Effort: High.

**Recommendation**: combine 2 + 3 — recompute remaining time from `Date.now()` deltas against a fixed phase-start timestamp (never accumulate via decrement) as the single source of truth, use `requestAnimationFrame` (or a short `setInterval`, ~250ms) purely as the re-render trigger, and add a `visibilitychange` listener that forces an immediate recompute+re-render on refocus. This satisfies the issue's explicit anti-drift requirement without the complexity of approach 4.

### Approaches: bell sound playback

1. **`HTMLAudioElement`** (`new Audio(url)` + `.play()`) — simplest, sufficient for a single bell cue on round transitions, works with a static asset added to `public/`, easy to fake in hook tests by mocking at a small adapter boundary. Caveat: browser autoplay policies may block the first `.play()` if it isn't gesture-adjacent — since the session starts from a user-initiated "Start" click, that first interaction can "unlock" audio for subsequent auto-triggered plays at round transitions.
2. **Web Audio API** (`AudioContext` + `AudioBufferSourceNode`) — lower latency, can pre-schedule playback precisely against `audioContext.currentTime` rather than relying on a JS callback firing exactly on time. Overkill for one sound effect; `AudioContext` also gets suspended in background tabs in some browsers, adding its own resume-handling complexity.

**Recommendation**: `HTMLAudioElement`, wrapped behind a small browser-only adapter (A1 pattern, precedent: `createGsiLoaderAdapter()`) so the UI hook doesn't hardcode an untestable `new Audio()` call inline and tests can inject a fake at the boundary.

### Approaches: where the state machine/orchestration logic lives

1. **Pure domain reducer + application use-case wrapper** — matches the codebase's established "every port call goes through a use case" precedent exactly, but there is no repository port involved in running a session, so the use-case would have nothing to orchestrate beyond calling the domain function. Effort: Medium.
2. **Pure domain reducer only, UI hook calls domain functions directly (no application use-case)** — avoids an application layer with no port to inject; the "every port call goes through a use case" precedent is specifically about repository-port calls (as documented in the archived design's D1/D4), not pure computation, so skipping a use-case here is arguably not a violation of that precedent, just a narrower application than existing timer-configuration slices. Effort: Low.
3. **Everything (state + timers) inline in the UI hook, no domain module** — rejected: the work/rest round progression IS the core business rule this issue is about; putting it only in a UI hook violates the Anemic Domain Model / God Hook anti-pattern and contradicts the project's own testing-strategy goal of testing business math with zero mocks/no jsdom.

**Recommendation**: Approach 2 — pure domain module (transitions + remaining-time computation, tested with fake/injected timestamps, zero React/browser deps) + a UI hook owning all browser-side effects (timer loop, visibility handling, audio, warning trigger). Skipping an application use-case here is a deliberate, smaller-footprint decision that should be explicitly confirmed in the proposal/design phase since it's a judgment call, not a mechanical follow of precedent.

### Recommendation Summary

Build a pure, framework-free domain state machine for round/phase progression (work ↔ rest, round increment, remaining-time computation from timestamps) tested with injected fake `Date.now()` values — no application use-case layer since there's no port to mediate. Build one new UI component folder (presentational + `.hook.ts` owning the `Date.now()`-delta timer loop, `visibilitychange` recompute, and a small browser-only audio adapter for the bell) following the exact file-split precedent already established by `rounds-stepper`/`timer-configuration-form`. Add `app/timers/[id]/active/page.tsx` mirroring the existing edit-page composition-root pattern (session resolution, auth vs. guest branch, `force-dynamic`). No changes needed to existing domain/application/infra timer-configuration code — this is purely additive. No dark-mode work needed — the app has no light theme to override.

### Risks

- The Stitch "Timer Activo" mock could not be visually inspected during this exploration (`stitch.withgoogle.com` project URL is authenticated/private, and per tool constraints WebFetch reliably fails on such URLs) — exact spacing/typography/component hierarchy needs confirmation via screenshot access before or during the design phase; only the issue body's text description (large countdown, ring, WORK/REST badge, round X/Y, pause/stop) could be used here.
- Browser autoplay policies could silently block the bell sound if playback isn't gesture-adjacent — needs an explicit "unlock on Start click" decision in the design phase, not left implicit.
- `requestAnimationFrame` throttling/suspension behavior while backgrounded varies by browser — must not treat rAF firing as guaranteed; the `visibilitychange`-forced recompute is mandatory, not an optional nicety.
- Skipping an application use-case for the state machine (Approach 2 above) is a deliberate deviation from the existing "every port call goes through a use case" precedent's spirit, even though it's not a literal violation (no port exists here) — flag for explicit reviewer sign-off in the proposal/design phase to avoid later architecture-review friction.
- No sound asset currently exists in `public/` — needs sourcing/licensing before implementation.
- `formatDuration` produces unpadded minutes (`"m:ss"`) — minor decision needed on whether the Timer Activo countdown wants zero-padded `"mm:ss"` framing instead.
